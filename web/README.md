# PropertyNest web app

Property portal for the Philippines: **buy, rent, and lease** only.
Next.js 15 (App Router, TypeScript) + PostgreSQL via Prisma 6.

## First-time setup

```bash
cd web
npm install
cp .env.example .env      # then fill in OTP_SECRET and IP_HASH_SALT (command in the file)
npm run db:init           # creates a private Postgres in ../.devdb (port 5433, local only)
npm run db:migrate        # creates the tables
npm run db:seed           # loads 120 sample listings, agents, agencies, locations, demo accounts
npm run dev               # http://localhost:3000
npm run worker            # second terminal: sends SMS/email and runs background jobs
```

`db:init` needs PostgreSQL installed (it finds `C:\Program Files\PostgreSQL\<version>\bin`, or set `PG_BIN`).
It does not touch any other Postgres server on your machine.

## Everyday commands

| Command | What it does |
|---|---|
| `npm run db:start` / `db:stop` | Start or stop the dev database (needed after a reboot) |
| `npm run dev` | Dev server with hot reload |
| `npm run worker` | Background worker (SMS, email, inquiry alerts). Keep it running alongside the app |
| `npm run build && npm start` | Production build, as it will run on the server |
| `npm run db:migrate` | After editing `prisma/schema.prisma`, create and apply a migration |
| `npm run db:seed` | Reset sample data (wipes listings, users, inquiries) |
| `npm run db:studio` | Browse the database in the browser |
| `npm run typecheck` / `npm run lint` | Checks to run before committing |

## Layout

```
prisma/schema.prisma        the whole data model (users, listings, inquiries, jobs, payments, ...)
prisma/seed.ts              sample data (generated by prisma/sample-data.js, same as the prototype)
src/app/(site)/             public site + account + moderation pages (with header and footer)
src/app/(auth)/             log in, sign up, phone OTP, forgot/reset password, verify email
src/app/api/                JSON API (listings, auth, uploads, inquiries, reports, favorites, admin)
src/lib/                    server logic: search, auth, OTP, passwords, moderation, jobs, messaging, storage
src/components/             header, cards, filters, listing form, moderation actions
scripts/worker.ts           background job worker
scripts/devdb.mjs           start/stop the local dev database
```

## Signing in

- **Email + password**: scrypt-hashed passwords. 5 failed tries per email (20 per IP) lock sign-in for 15 minutes.
  Reset links are emailed, work once for 1 hour, sign out other devices, and clear the lockout. New accounts get an email confirmation link.
- **Phone OTP**: 6-digit SMS code, expires in 5 minutes, at most 1 per minute and 5 per hour per number, 5 wrong tries per code.
- **Google**: set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (see `.env.example`). Until then the button explains it isn't set up.
- Sessions: a random token in an httpOnly cookie; only its SHA-256 is stored. 30 days.

## Maps

- **Property page "What's nearby"**: schools, hospitals, malls, banks, parks, gyms, train and bus stations within 1 km, with walking times, category chips and a closest-places panel.
- **Privacy**: posters choose "exact location" or an approximate ~400 m circle. When hidden, the exact coordinates never leave the server; pages and APIs get an offset point.
- **Posting**: click or drag a pin, or use the device location. Pins more than 30 km from the chosen city are flagged for review.
- **Search**: a Map view next to grid and list shows price pins.
- **Data**: nearby places come from OpenStreetMap (Nominatim), cached per ~1 km cell in `NearbyCell` and fetched by the worker's slow lane (~20 s per cell, 1 request per second). Map tiles come from OpenStreetMap.

## Posting and moderation

- Owners get 3 active listings; agents 30 (until paid plans arrive in Phase 2). Seekers who post become owners.
- Photos are re-encoded on upload (1600 px and 640 px WebP); camera metadata, including GPS location, is removed.
- Automatic checks hold a listing for review when they see: an unusual price, scam wording (pay before viewing, remittance),
  contact details in the text, photos already used by another poster, a poster's first listing, or a resubmission after rejection.
- Moderators approve, ask for changes, or take down; the poster gets an SMS either way. 3 user reports hide a listing until reviewed.
- Inquiries alert the agent or owner by SMS and email through the job queue, and land in **Account → Inquiries**.

## How it's built to scale

- Public pages render on the server (good for Google) and are cached: home page 60s, each property page 60s after first view, header counts 5 min.
- Sign-in state is fetched by the browser (`/api/auth/me`), so public pages stay cached for signed-in users too.
- All search filters live in the URL, so searches can be cached by a CDN and shared.
- Search uses indexed columns, plus trigram indexes for text; location search ignores accents (`paranaque` → Parañaque).
- Slow work (SMS, email, alert fan-out) goes through a Postgres job queue drained by `npm run worker`; several workers can run safely.

Local load test (one Node process, 50 concurrent users, no CDN): cached home page ≈ 900 req/s,
full search page ≈ 180 req/s, search API ≈ 600 req/s, zero errors.

## Going-live checklist (Phase 1 items)

- `SMS_PROVIDER=semaphore` with `SEMAPHORE_API_KEY`; `EMAIL_PROVIDER=resend` with `RESEND_API_KEY` and a verified sending domain.
- Remove `OTP_DEV_ECHO`. Set fresh `OTP_SECRET` and `IP_HASH_SALT`. Set `SITE_URL=https://...` (this turns on secure cookies).
- Google sign-in: create the OAuth client and add the production redirect URI.
- Move photo storage to S3 or R2 (`src/lib/storage.ts`) and serve `/media` from a CDN.
- Run at least one `npm run worker` process next to the app.
- Maps: switch tiles to a keyed provider (MapTiler, Stadia or Geoapify) in `src/components/map/mapKit.ts`, and nearby places to Geoapify or a self-hosted Nominatim in `src/lib/nearby.ts`. The free OpenStreetMap services only allow light use.
- Have a lawyer replace the draft terms, privacy, and cookie pages.
